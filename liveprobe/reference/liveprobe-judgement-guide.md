# LiveProbe 장애 판단 참고자료 (v1)

이 문서는 AI 에이전트와 운영자가 Kubernetes 장애를 판단할 때 참고하는 자료다. 모든 항목은 실제 실행 기록에서 관측한 사실이며, 각 항목 끝에 원본 기록을 적는다. 기록 표기는 `저장소#사례/방식`이고 `iid`는 LiveProbe 사건 번호다.

- 정책 A: SIMPLE만 자동 조치, 조치는 롤백 하나.
- 정책 B: COMPLEX까지 자동 조치, 조치는 롤백 하나.
- 정책 C: HIGH_RISK만 인계. 롤백·재시작·파드 삭제·복제 수·메모리 한도 조치를 쓸 수 있다.

## 공통 원칙

1. 쿠버네티스 조치는 하나만 고르고, 검증된 원인을 고칠 때만 실행한다. 원인을 못 찾았으면 인계한다.
2. 피해가 실행 중인 프로세스나 파드 설정에 있으면 쿠버네티스 조치로 서비스를 살릴 수 있다. 앱 코드나 외부 의존성에 있으면 인계한다.
3. 엔드포인트가 0이어도 원인이 같지 않다. 파드가 죽어서 0인지, 라우팅(셀렉터)이 어긋나서 0인지 먼저 구분한다. 라우팅 문제는 항상 HIGH_RISK다.
4. 1분 평균 지표는 짧거나 간헐적인 장애를 묽게 보여준다. 지표가 정상이어도 로그의 오류가 반복되면 근거로 본다.
5. 독립 검증자가 같은 조치를 지지해야 실행한다. 검증자가 "근거 부족"이라고 하면 인계가 맞다.

## 항목 1. 이미지 문제 (ErrImagePull / ImagePullBackOff, 최근 롤아웃 직후)

- **관측 신호**: 새 파드가 `ErrImagePull` 또는 `ImagePullBackOff`, 이전 레플리카셋은 살아 있다. 최근 몇 분 안에 Deployment 리비전이 올라갔다.
- **확인할 근거**: Deployment의 현재·이전 이미지, 이전 리비전 존재 여부, 파드 대기 메시지.
- **흔한 가짜 단서**: 이전 파드가 아직 Ready라 서비스가 살아 보인다. 다른 파드의 재시작 기록이 섞여 있다.
- **원인 후보 순위(관측)**: 대부분 1순위가 `image_pull_failure`였다(정책 A 32건 중 29건).
- **효과 있던 조치**: `rollout_undo`. 23건 모두 성공하고 검증을 통과했다.
- **잘 맞은 구성**: SIMPLE 경로나 단일 에이전트로 충분했다. single_small 8/8, adaptive 8/8을 각각 평균 $0.002, $0.043에 해결했다. fixed 다중 에이전트는 0/8이고 평균 $0.227이었다. COMPLEX 그룹이 조치 대신 인계를 택했다.
- **실패 사례와 이유**: Codex 호출 실패 1건은 인계로 끝났다. COMPLEX 그룹은 원인을 맞혀도 롤백을 제안하지 않는 경향이 있었다(정책 A 시점).
- **원본 기록**: `store-pilot#F1-01/single_small` (iid 69), `store-pilot#F1-01/single_high` (iid 70)

## 항목 2. 시작할 때마다 프로세스가 죽는 크래시 (CrashLoopBackOff, 같은 exit code 반복)

- **관측 신호**: `CrashLoopBackOff`, 매번 같은 exit code(예: 70), startup probe가 HTTP 500으로 실패한다. 이미지와 리비전은 바뀌지 않았다.
- **확인할 근거**: 직전 컨테이너 로그, exit code, 최근 배포·설정 변경 여부, 같은 파드 안의 재시작인지 새 파드에서도 반복되는지.
- **흔한 가짜 단서**: 엔드포인트 0과 호출자 오류는 결과일 뿐 라우팅 문제가 아니다.
- **원인 후보 순위(관측)**: `process_crash`, `endpoint_unavailable` 순이었다.
- **AI 판단(관측)**: 정책 B·C 48건 모두 인계했다. 근거만으로는 앱 시작 실패와 구분되지 않는다는 판단이었다.
- **주의**: 재시작으로 풀리는 크래시도 있다. 장애 상태가 파드 안(임시 볼륨 등)에 있으면 새 파드로 회복될 수 있다. 근거에서 "새 파드에서도 반복되는지"를 확인하기 전에는 인계가 안전하다.
- **원본 기록**: `store-chaos#F1-02/single_small` (iid 141), `store-policyC#F1-02/single_small` (iid 874)

## 항목 3. 메모리 부족 (OOMKilled)

- **관측 신호**: 직전 종료 사유가 `OOMKilled`, 재시작이 반복되고, 설정된 메모리 한도 근처에서 죽는다.
- **확인할 근거**: Deployment 근거의 `resources.limits.memory`와 `requests.memory`, 승인 범위(256..768Mi), 재시작 횟수.
- **흔한 가짜 단서**: 엔드포인트 0과 호출자 실패는 파드가 죽은 결과다. 이것만으로 HIGH_RISK로 올리면 안 된다(정책 B에서 8건이 이 이유로 HIGH_RISK 인계됐다).
- **원인 후보 순위(관측)**: `memory_exhaustion`이 1순위였다(정책 B 60건 중 51건, 정책 C 28/28).
- **효과 있던 조치**: `set_memory_limit`으로 현재 한도보다 크고 2배를 넘지 않는 최소 허용값(512Mi→768Mi)을 적용했다. 정책 C 28건 모두 검증을 통과했다.
- **잘 맞은 구성**: 4방식 모두 7/7. 평균 비용은 single_small $0.002, single_high $0.046, adaptive $0.283, fixed $0.286이다. 이 유형은 가장 싼 방식으로도 충분했다.
- **실패 사례와 이유**: 정책 B에서는 쓸 수 있는 조치가 롤백뿐이라 60건 모두 인계했다. 한도가 이미 최대(768Mi)면 인계해야 한다.
- **원본 기록**: `store-policyC#F2-01/single_small` (iid 894), `store-policyC#F2-01/single_high` (iid 895)

## 항목 4. DB 연결 풀 고갈

- **관측 신호**: 로그에 연결 획득 실패(`CannotGetJdbcConnectionException`)가 반복되고, 호출자가 503을 받는다. 지표상 `db_pool_active`가 `db_pool_max`와 같고 `db_pool_pending_threads`가 0보다 크다. 파드는 Ready다.
- **확인할 근거**: 풀 지표(사용 중·최대·대기·획득 실패), 오류 시작 시점이 파드 시작보다 뒤인지, DB 자체가 정상인지.
- **흔한 가짜 단서**: 직전 롤아웃이나 짧은 startup probe 실패. 오류가 새 파드 시작 직후에만 있으면 DB 쪽 문제일 수 있다.
- **원인 후보 순위(관측)**: `db_pool_exhaustion`, `dependency_latency` 순이었다.
- **효과 있던 조치**: `rollout_restart`를 임시 조치로 썼다(새 프로세스가 풀을 초기화). 정책 C에서 실행된 재시작 7건 모두 검증을 통과했다. `why`에 "근본 원인은 개발자 확인 필요"를 남긴다.
- **실패 사례와 이유**: 검증자가 "풀이 고갈됐다는 근거가 없다"며 막은 경우가 있었다. 풀 지표가 근거에 없던 시점(지표 수집 문제 수정 전)이 대표적이다. 풀 지표가 정상인데 오류만 있으면 DB 연결 문제일 수 있으므로 인계한다.
- **원본 기록**: `store-policyC#F3-02/fixed_multi_agent` (iid 928), `store-policyC#F3-04/single_high` (iid 931)

## 항목 5. 응답 지연 (원인 신호 없음)

- **관측 신호**: 지연 경보는 있지만 오류율이 0이고 파드가 Ready이며 재시작도 없다. 1분 평균 지연은 수십 ms 수준으로 보인다.
- **확인할 근거**: p95나 엔드포인트별 지연, 지연 시작 시점, 하위 호출(DB·다른 서비스) 지연.
- **흔한 가짜 단서**: 경보 직전 롤아웃이나 짧은 probe 실패. 시점이 겹쳐도 원인이라는 근거는 아니다.
- **AI 판단(관측)**: 정책 C 40건 중 33건 인계. 원인을 가리키는 신호가 없는데 재시작하지 않는 것은 운영 관행과 맞는다.
- **개선 여지**: 평균 대신 p95 지표를 근거에 넣으면 판단이 달라질 수 있다(미검증).
- **원본 기록**: `store-chaos#F3-01/single_small` (iid 229)

## 항목 6. 엔드포인트 0 (라우팅 문제, 셀렉터 불일치)

- **관측 신호**: 파드는 Ready인데 Service 엔드포인트가 0이고, Service 셀렉터와 일치하는 파드가 없다. 호출자가 실패한다.
- **판단**: 트래픽 경로 변경과 여러 서비스 영향 위험이 있으므로 HIGH_RISK, 운영자 인계. 규칙으로 고정돼 있다.
- **원인 후보 순위(관측)**: `service_selector_mismatch` (정책 A 32건 중 31건).
- **AI 판단(관측)**: 정책 A·B 60건 모두 인계했다. 자동 조치는 0건이었다.
- **원본 기록**: `store-pilot#F4-01/single_small` (iid 81), `store-chaos#F4-02/single_small` (iid 289)

## 방식 선택 요약 (관측 기준, 일반화 주의)

| 유형 | 충분했던 방식 | 비고 |
|---|---|---|
| 이미지 문제 | 단일 에이전트(small) | 다중 그룹이 오히려 인계를 많이 했다 |
| OOM | 단일 에이전트(small) | 4방식 결과가 같았다 |
| 연결 풀 | 그룹 또는 single_high | 검증 단계가 근거 부족을 걸러냈다 |
| 크래시·지연 | 판단 불가(대부분 인계) | 근거 보강이 먼저다 |
| 라우팅 | 규칙(HIGH_RISK) | AI 판단과 무관하게 인계 |

## 이 문서의 한계

- 정책 A·B 실행 시점에는 앱 지표가 수집되지 않았을 수 있다(Istio 메트릭 병합 문제, 2026-10-11 수정). 그 시점 기록에서 지표가 0인 것은 실제 0이 아닐 수 있다.
- 방식당 표본은 5~16건이다. 방식 간 차이를 일반화하지 않는다.
- 비용은 토큰 환산 추정치다.
