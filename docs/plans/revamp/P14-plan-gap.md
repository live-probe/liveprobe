## 2. 이번에 구현할 항목 (순서대로)

각 항목은 테스트(오프라인) → 배포 → 실측 확인 순서로 끝낸다. LLM 재평가가 필요한 항목은 따로 표시한다.

### B1. Node 상태와 설정(ConfigMap) 변경 근거 추가
- Node: 사건 파드가 올라간 노드의 Ready·MemoryPressure·DiskPressure·PIDPressure 조건과 할당 가능 CPU·메모리. 관찰 계정은 이미 nodes 읽기 권한이 있다.
- ConfigMap: 사건 workload가 참조하는 ConfigMap의 이름, 내용 해시, 승인 버전과 일치 여부, 마지막 변경 시각. **값은 근거에 넣지 않는다**(비밀값 유출 방지). 대상 네임스페이스 한정 Role(configmaps get/list)을 관찰 계정에 추가한다.
- 근거 번호: E8_node, E9_config. 기존 E1~E7 번호는 바꾸지 않는다(인용 검사·평가 기록 호환).
- 완료 기준: 단위 테스트, 배포 후 실제 사건 근거에 두 항목이 들어가는 것 확인, Secret 읽기 권한이 여전히 없음(`kubectl auth can-i`) 확인.

### B2. 이벤트·로그 중복 제거
- 같은 (reason, object, message) 이벤트는 하나로 합치고 count를 더한다. 같은 로그 줄(타임스탬프 제외 본문 기준)은 하나로 합치고 반복 횟수를 붙인다.
- 완료 기준: 단위 테스트, 프롬프트 근거 크기 감소를 실제 사건 근거로 비교.

### B3. 독립 조회 병렬화
- Kubernetes 조회 묶음, Prometheus, Loki를 스레드 풀로 동시에 실행한다. 각 출처의 실패는 지금처럼 그 항목의 error로 남긴다.
- 완료 기준: 단위 테스트(실패 격리), 배포 후 근거 수집 시간 비교(로그의 `in %.1fs`).

### B4. 사건 화면에 라우팅 판단 표시
- 수준·Workflow·판단 주체(rules / rules+llm / router_failure)·이유·신뢰도, 모델 후보별 점수(품질·비용·처리량·제외 이유)와 선택 모델을 표로 보여 준다. API는 이미 `routing[].rationale/policy`를 반환한다.
- 완료 기준: 빌드, 실제 사건 화면 1440/390px 확인.

### B5. 네트워크 drop을 사건 신호로 연결
- Hubble 흐름에서 같은 (출발, 도착) 쌍의 drop+error가 기준(현재 지도 경고와 같은 5건) 이상이면 `NetworkDrop` 신호를 낸다. 대상 네임스페이스 workload만, 같은 쌍은 병합 창 동안 한 번만.
- 라우터: `NetworkDrop` 신호는 트래픽 경로 장애이므로 HIGH_RISK(운영자 이관)로 판정한다. 과제계획서의 고위험(트래픽 경로·여러 workload 영향)과 같고, 허용 조치(재시작·메모리 등)는 네트워크 차단을 고치지 못하므로 자동 조치 대상이 아니다.
- 완료 기준: 단위 테스트, 실제 NetworkPolicy 차단 주입 → 사건 생성 → HIGH_RISK 이관 → 원복 확인.

### E1. 시험 사건별 결과표
- 기존 저장소(`progress.jsonl`)에서 사건 × 방식별 선택 수준·Workflow·사용 모델·비용·시간·원인 후보·결과를 표로 뽑는다(LLM 호출 없음). 정책 A·B·C를 섞지 않고 구간별로 낸다.
- 산출물: `docs/plans/revamp/P14-case-table.md` + CSV.

### E2. 소스 설명(README) 갱신
- 현재 구조(정책 C, 모델 라인업, 다이어그램 링크, 실행·확인 방법)로 README를 다시 쓴다.

## 3. 이번에 하지 않는 항목 (다음 판단 필요)

- **C1 Workflow 선택 정확도 개선**: 라우터 규칙 변경은 평가 정답과 맞추는 과적합 위험이 있다. 먼저 기록된 근거로 규칙만 다시 돌리는 오프라인 재현으로 원인을 나누고(LLM 비용 0), 개선안은 P13 새 사례로만 검증한다. 실제 재평가는 LLM 비용·시간이 크므로 별도 승인 후 진행.
- **C2 비용 목표**: 그룹 구조상 호출 수가 많아 단일 고성능 대비 절감이 어렵다. 새 라인업(astra 단가 5배)에서는 single_high가 비싸져 비교 결과가 달라질 수 있다. 평가 방식(arms.py)은 기존 기록 보존을 위해 고정했으므로, 새 라인업 재평가 여부를 먼저 정해야 한다.
- **C3 자동복구 100%**: 크래시(앱 코드)·원인 미상 지연은 정책상 이관이 정답일 수 있다. 정답 라벨 재검토가 먼저다.
- **D1·D2 추후 확장(조합 추천, 신규 장애 감지)**: 계획서대로 라우팅에 영향 없는 병행 기록부터. 데이터(사건 수)가 더 쌓인 뒤.
