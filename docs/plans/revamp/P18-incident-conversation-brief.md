# P18 추가 인터뷰 정리 — 흐름과 통합 채팅 중심 장애 관제실

상태: 사용자 요구를 현재 인터뷰·계획에 추가한 문서다. 화면 구현·배포·검증 완료를 뜻하지 않는다. 기존 환경·시스템·코드 수정 PR 범위와 함께 수행하되, 기존 3열 관제실을 유지한다는 화면 가정은 이 문서로 대체한다.

## 사용자 요구와 문제

- 감지 신호·사건 수준 판단을 선택해도 의미 있는 내용이 없어서는 안 된다.
- `근거 수집 9건`이라면 숫자뿐 아니라 그 9건이 무엇인지 간략하게라도 보여야 한다.
- 신호 분석·결과 확인에서 같은 `이 단계가 본 근거` 목록만 되풀이하는 화면은 단계의 차이를 설명하지 못한다.
- 기본 화면은 `01 AI 분석 흐름`과 기존 02/03을 합친 채팅 화면이다.
- 01의 실행 블록을 선택하면 같은 실행을 나타내는 채팅 카드로 부드럽게 스크롤한다.
- 채팅 카드에는 개요와 한글 결론을 읽기 좋은 형식으로 보여 준다.
- 카드의 `상세보기`를 눌렀을 때만 현재 03 운영자 대화와 같은 폭의 사이드 패널이 나타난다. 닫으면 사라진다.
- 운영자는 02 통합 채팅 안에서 메시지를 입력한다.

## 현재 화면·코드에서 확인한 사실

- 실제 배포 화면 `/incidents/1019`에서 감지 신호·사건 수준 판단 선택을 재현했다. 두 단계 모두 `이 단계에는 별도 결론이 없습니다.`, `이 단계에 연결된 원문 근거가 없습니다.`가 표시됐다. 첨부 사진을 추측한 것이 아니라 현재 실행 화면에서 별도 확인한 결과다.
- 증거: `docs/evidence/P18/incident-conversation-before/observed.json`과 감지/판단 선택 캡처. 이는 기존 화면의 문제 재현 기록이며 새 화면 검증 증거가 아니다. 재캡처의 1280px 화면에서는 기존03 폭316px을 확인했다.
- 1440×900에서 기존 03 운영자 대화 패널의 측정 폭은 340px이다. 반응형에서는 기존 폭 규칙을 참고하며 모든 폭을 340px로 고정하지 않는다.
- `dashboard/src/IncidentRoom.tsx`는 모든 단계에 공통 `StepDetail`과 입력 근거 필터를 적용한다. 노드 선택은 `choose()`에서 근거 탭으로 이동하며 통합 채팅 위치로 이동하지 않는다.
- `liveprobe/app/flowgraph.py`는 감지·근거 수집 노드에 주로 라벨·상태만 담고 기본 `inputs=[]`, 결론 없음으로 만든다. 근거 수집 개수는 `Evidence` 레코드 개수다. 채팅 원문 행 개수와 같은 단위가 아니다.
- `dashboard/src/narrative.ts`의 역할명 기반 인용 보조 연결만으로는 같은 역할의 재시도·상위 모델 재실행을 정확한 채팅 항목과 대응시키기 어렵다. 실행별 식별자가 필요하다.

## 목표와 비목표

목표는 한 화면에서 분석의 진행 경로를 보고, 해당 실행의 설명을 읽고, 같은 대화에서 운영자가 개입하는 것이다. 상세 원문과 기술 메타데이터는 읽는 흐름을 방해하지 않으면서 필요할 때 열 수 있어야 한다.

비목표:
- 근거·운영자 채팅을 기존처럼 서로 다른 상시 열에 남기는 방식.
- 공통 근거 목록을 복사한 카드에 역할명만 바꾸는 방식.
- 개요·결론을 읽기 위해 매번 상세 패널을 열게 하는 방식.
- 비어 있는 과거 기록을 그럴듯한 결론·정상 상태로 채우는 방식.
- 비공개 내부 사고 과정이나 기록되지 않은 판단 과정을 생성·표시하는 것. 공개된 출력·수집 데이터·기록된 판단 근거만 사용한다.
- 분석·조치 권한, HIGH_RISK 인계, 승인·Secret 처리 정책 변경.

## 화면 구조

### 기본 상태: 상시 두 영역

- 01 `AI 분석 흐름`: 기존 세로 흐름도, 병렬·재실행·승격·지시 연결과 확대 제어를 유지한다.
- 02 `분석 · 운영자 대화`: 실행 카드와 운영자 메시지가 같은 시간순 대화 안에 놓인다. 개요·한글 결론이 기본으로 보이며 원문 JSON을 기본 본문으로 내보내지 않는다.
- 메시지 입력란과 분석 제어는 02 하단에 고정한다. 기존 독립 03 운영자 대화 열과 상시 근거 열은 없앤다.
- 조치 승인·인계 인수·운영자 종료·변경 PR·환경 승격도 통합 대화 안의 구별 가능한 카드로 유지한다. 확인 대기 항목은 묻히지 않게 표시한다.

### 상세 상태: 필요할 때만 여는 패널

- 채팅 카드의 `상세보기`가 해당 실행의 상세 패널을 연다. 흐름 노드 클릭만으로 상세 패널이 자동으로 열리지는 않는다.
- 데스크톱에서는 기존 03과 동급 폭의 오른쪽 패널을 사용한다. 기본 02는 나머지 폭을 사용하며 페이지 가로 넘침을 만들지 않는다.
- 패널 상단에 단계·실행 상태·닫기를 고정한다. 긴 본문은 패널 내부에서 스크롤한다.
- `닫기` 또는 Esc로 패널을 닫으면 기본 2영역으로 돌아간다. 채팅 스크롤·작성 중인 메시지·흐름 선택 상태를 보존하고 포커스를 연 버튼으로 돌린다.
- 다른 카드의 상세보기를 누르면 기존 패널 내용을 그 실행으로 교체한다. 여러 패널을 쌓지 않는다.
- 좁은 화면에서는 패널을 전체 폭 서랍으로 표시한다. 기본 영역은 흐름/대화 두 전환으로 접근하며 노드 선택 시 대화로 이동한다. 이 반응형 선택은 구현 가능한 권장 기본값이며 사용자에게 추가 결정을 요구하지 않는다.

### `근거 수집 9건`의 수용 기준

- 실제 해당 수집 실행에 항목 9개가 있으면 카드 안에서 9개 모두에 대한 짧은 목록을 볼 수 있어야 한다. 숫자만 9이거나 공통 근거 창을 여는 버튼만 있는 것은 불합격이다.
- 각 행은 항목 식별자/종류, 출처, 한두 줄 내용, 수집 상태를 제공한다. Deployment·Pod·이벤트·지표·로그 등 종류는 실제 수집 항목에서 얻으며 9개를 만들기 위해 가상 항목을 추가하지 않는다.
- `수집 항목 9개`, `재수집 이력 N회`, `원문 N줄`은 서로 다른 단위다. 중복 그룹 수를 원래 수집 건수로 바꾸지 않는다. 상단 개수와 열람 가능한 항목 개수는 같은 집합을 기준으로 계산한다.
- 정상 결과뿐 아니라 미수집·실패 항목에도 상태와 사유를 보여 준다. 일부만 응답한 경우 전체 수와 현재 열람 가능한 수, 누락 이유를 구분한다.
- 공유 근거는 상세에서 한 원문에 연결하되, 각 실행 카드의 요약·결론은 그 실행 출력에 기반한다. 같은 근거를 사용한다는 이유로 서로 다른 단계의 결과를 생략하지 않는다.

## 흐름과 채팅의 대응·스크롤

- 흐름 노드와 채팅 카드를 안정된 실행 ID로 연결한다. `node_id`, `agent_run_id`, `event_seq`, 수집/판단의 기록 ID 등을 사용하며 역할명이나 카드 순번만으로 연결하지 않는다. 필드 이름은 설계 제안이며 현재 모든 API에 구현됐다는 의미는 아니다.
- 같은 역할 재시도·상위 모델 승격·여러 번 수집은 별도 카드로 구분한다. 노드를 누르면 선택한 정확한 실행으로 이동해야 한다.
- 노드 클릭/Enter → 02의 대응 카드로 부드럽게 스크롤 → 일시적인 강조·보이는 포커스로 도착 위치를 알린다. 페이지 전체나 01 캔버스가 함께 튀지 않는다.
- 네이티브 스크롤과 CSS 강조를 우선하고 새 스크롤 라이브러리는 추가하지 않는다. 움직임 감소 설정에서는 즉시 이동하며 강조의 동작 효과도 줄인다.
- 실시간 갱신은 기존 카드를 안정된 ID로 갱신한다. 운영자가 과거 카드를 읽는 중이면 강제 최신 이동을 하지 않고 새 기록 알림을 제공한다. 자기 메시지 전송·명시적 최신 이동은 최신 메시지로 이동한다.
- 실행 전/실행 중/실패/건너뜀 카드에는 실제 상태와 이유를 보인다. 완료 전 결론을 미리 만들지 않는다. 기록 없는 과거 단계는 알고 있는 개요와 무엇이 미기록인지 설명하며 빈 패널로 끝내지 않는다.

## 데이터와 기존 안전 계약

- `flowgraph.py`의 라벨만 채우는 보완으로 끝내지 않는다. 감지 원문·Evidence 레코드·RoutingDecision·AgentRun·RunEvent·조치/PR 기록에서 단계별 구조화 내용을 구성하고, 흐름과 채팅이 같은 실행을 가리키게 한다.
- 요약 생성 출처는 규칙/AI/원문을 구별한다. 미기록·한글 해석 대기·조회 실패를 관측 결과와 구분한다.
- 단계의 원문 참조와 화면 건수는 서버 기록에 추적 가능해야 한다. 원문은 마스킹된 저장 기록을 그대로 보여 주며 요약 때문에 원문을 덮어쓰지 않는다.
- 역할별 카드 차이는 기록된 결과의 표현 차이다. 동일 근거를 여러 역할이 읽는 실제 분석 동작 자체를 변경하라는 요구로 해석하지 않는다.
- 메시지 전송·분석 제어·실행 전 영향 설명·`정말 진행하시겠습니까?`·계획 해시·PR 검토/단계 승인·Secret 전용 입력·종료 사건 지시 차단을 그대로 유지한다.

## 검증 시나리오

- U1: 기본 화면은 01과02이며 상시 원문 열·기존03 채팅 열이 없다.
- U2: 감지·근거 수집·사건 수준 판단·Group·각 분석 역할·검증·조치·종결을 각각 선택해 대응 카드를 읽는다. 알고 있는 내용이 있음에도 빈 공통 상세로 끝나는 단계가 없어야 한다.
- U3: 실제 수집 항목 9개인 고정 데이터로 목록 9개와 이름·짧은 내용·상태를 검증한다. 로그 줄/그룹 수와 혼동하지 않는다. 부분 실패·재수집도 별도 검증한다.
- U4: 같은 근거를 인용하는 신호 분석과 결과 확인을 나란히 검증한다. 전자는 관측·원인 분석, 후자는 검증 대상·수락/반려·근거를 보여야 한다.

## 범위 추가와 다음 단계

현재 P18 인터뷰와 실행 계획의 추가 작업 W6로 편입한다. 새 인터뷰 질문은 필수가 아니다. 핵심 화면 구조·상호작용·내용 기대가 사용자 메시지에 명시되어 있고, 반응형/모션의 작은 선택은 위 권장 기본값으로 되돌릴 수 있다.

구현 전 이 문서를 디자인 계약에 반영하고 단계별 데이터 대응을 먼저 설계한다. 기존 W2/W3/W4 완료와 W6의 구현·배포·시각 검증 완료를 혼동하지 않는다. 이번 변경은 요구사항·계획 반영이며 새로운 화면 구현을 수행한 것으로 보고하지 않는다.
