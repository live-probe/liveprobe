# P15 LiveProbe 사용자 경험 재설계 인터뷰

상태: 인터뷰 완료(2026-10-18, 6개 질문). 아래 "정리된 브리프"가 계획 단계의 입력이다. "가정"으로 표시한 항목은 인터뷰에서 직접 확인하지 않았으며, 계획 단계에서 근거를 확인하거나 사용자에게 보고한다.

## 요청 원문 요약 (2026-10-18)

- 서비스 메시·자원/네트워크 지도 중심의 현재 화면에서는 LiveProbe가 무엇을 보여주려는지 드러나지 않는다.
- "운영자 인계" 같은 결과만 보여서 AI가 실제로 무엇을 했는지 알기 어렵다.
- 출발점: 운영자가 AI 분석 과정을 지켜보면서 에러 로그 원문과 한글 정리를 함께 보고, 어떤 상황인지 바로 이해할 수 있어야 한다.
- 이어서 AI가 Agent Group을 선택하는 흐름과 하위 Agent 분기를 시각적으로 확인하고, Agent별로 하는 일을 볼 수 있어야 한다.
- 단순 운영자 인계로 끝내지 않는다. 운영자의 지시를 받아 AI가 작업을 수행하는 사람 개입(Human in the middle) 흐름이 필요하다.
- 전체 Kubernetes 운영 관제 대시보드와 장애 대응 관제 대시보드를 분리한다.

## 현재 저장소에서 확인한 사실

- 메뉴는 서비스 메시(Kiali iframe, 첫 화면), 자원·네트워크 지도, 사건, 검토 기록, 설정이다(`dashboard/src/App.tsx`, `Shell.tsx`).
- 1440px 캡처에서는 첫 화면 로드 2초 후에도 메시 영역이 비어 있었다. 원인은 조사하지 않았다(Kiali 제거 대상).
- 사건 상세 피드는 Agent 출력이 영어 원문 그대로 보인다. 역할은 `evidence_curator` 같은 영문 식별자로, 라우터는 "router 완료"로만 표시된다. 오른쪽 패널에는 라우팅 판단, 후보 모델 점수표, Workflow 경로 목록이 있다.
- 운영자 메시지는 진행 중인 사건에만 보낼 수 있고 다음 노드 경계에 반영된다. `resolved/handed_off/failed`가 되면 메시지와 제어 API가 409를 반환한다(`liveprobe/app/main.py:226-252`).
- 인계 후에는 "인수(claim)"만 가능하며, 이 동작은 클러스터 조치를 승인하지 않는다(`main.py:384-406`).
- 실행 가능한 조치 유형은 `rollout_undo`, `pod_delete`, `rollout_restart`, `scale_replicas`(1..2), `set_memory_limit`(256..768Mi), `configmap_restore`(승인 버전만)이다(`liveprobe/app/actions.py:69-79`).
- 현재 정책상 HIGH_RISK는 자동 조치 없이 인계하고, 앱 코드 수정도 인계한다.
- Prometheus는 두 개다. 클러스터 자원 모니터링은 `liveprobe-observability/prometheus`가 담당한다(kube-state-metrics, kubelet cAdvisor, `liveprobe-target` Pod 수집). `istio-system/mesh-prometheus`는 istiod와 Envoy sidecar 지표만 수집하는 Kiali 전용 인스턴스다.
- istiod·kiali·mesh-prometheus 3개의 메모리 합계는 약 553Mi다. 노드 전체는 CPU 34%, 메모리 44%다(2026-10-18 `kubectl top`, 단일 노드 `lima-rancher-desktop`).
- 로그 수집(Alloy)은 `liveprobe-target`의 `order|inventory` 앱만 대상이다. API 설정의 원천 주소는 Prometheus·Loki·Hubble relay다(`liveprobe/app/config.py:258-264`).

## 명확화 기록

1. Q: 인계 후 운영자가 지시하면 AI가 어디까지 직접 실행하는가? A: 허용 목록 밖의 Kubernetes 변경(YAML 패치, 다른 리소스 생성 등)까지 포함한다. 순서는 계획 → dry-run → 승인 → 실행 → 원복이다. 실행 전에는 반드시 운영자가 지시한 명령의 부작용(side effect)을 설명하고 "정말 진행하시겠습니까?"를 물어야 한다.
2. Q: 운영자가 확인하면 AI가 변경할 수 있는 범위는 어디까지인가? A: Secret을 제외한 모든 범위(모든 Namespace, Node, 클러스터 범위 리소스 포함)로 확장한다. Secret 변경이 필요하면 AI가 채팅으로 운영자에게 새 값 입력을 요청한다. 입력값은 내부 프로세스가 직접 처리해 AI(LLM)가 확인할 수 없도록 구성한다.
3. Q: 평상시 전체 운영 관제 화면은 첫눈에 어떤 질문에 답해야 하는가? A: "클러스터가 안전한가"(건강도 요약)와 "어디에 무엇이 연결돼 있고 어디가 아픈가"(토폴로지)를 합친다. 장애가 발생하면 지도 위에 해당 위치를 표시하고, 클릭하면 장애 관제 화면으로 이동한다. 현재 자원·네트워크 지도는 디자인이 좋지 않으므로 상용 서비스 디자인을 최대한 참고해 새로 만든다. 서비스 메시(Kiali)는 너무 무거우므로 제거한다.
   - 추가 정정: 클러스터 자원 모니터링에 필요한 구성(Prometheus 등)은 최대한 유지한다. 관제 시스템은 원천(raw) 데이터를 최대한 그대로 사용해 구성한다.
4. Q: 장애 관제 화면에 들어온 운영자가 처음 보는 화면은 어떤 짜임인가? A: 상단 한글 상황 요약 + 3단 구성(왼쪽 원문과 한글 해석, 가운데 실시간 분기 흐름도, 오른쪽 운영자 채팅)을 기준으로 한다. 운영자가 채팅하면 실행 중인 AI 분석에 steering으로 반영되도록 구성한다.
5. Q: 개편 완료를 무엇으로 확인하는가? A: 실제 클러스터 처음부터 끝까지 시연 방식으로 한다. 대상은 지금까지 만든 장애 중 사용자 개입 없이 완결된 장애 10개다. 해당 장애를 재발생시켜 지도 위치 표시 → 장애 관제 이동 → 원문과 한글 해석 → 흐름도 실시간 분기 → 자동 처리 완결까지 확인한다. 사람 개입(steering, 인계 후 지시, 부작용 확인, Secret 입력)은 사용자가 직접 확인하자고 할 때 함께 확인한다.
6. Q: 무인 완결 기록의 장애 유형이 3종뿐일 때 10건은 어떻게 채우는가? A: 3개 유형 × 2개 서비스를 기본으로 하고, 강도·방해 신호 변형을 더해 10건을 구성한다. 재실행 결과가 인계로 끝나면 그 건은 실패로 기록하고 원인을 조사하며, 다른 사례로 바꿔 끼우지 않는다.

## 정리된 브리프

### 목표

1. 전체 운영 관제(첫 화면): 클러스터 건강도 요약과 새 토폴로지 지도를 한 화면에 둔다. 요약 항목은 노드·Namespace·워크로드 상태, 최근 이상 신호, 진행 중 사건과 AI 처리 단계다. 장애가 생기면 지도에서 해당 자원 위치를 강조하고, 클릭하면 그 사건의 장애 관제 화면으로 이동한다. 지도는 상용 관측 서비스 디자인을 참고해 새로 만들고, 기존 `ClusterMap`을 대체한다.
2. 장애 관제(사건 1건):
   - 상단 한글 상황 요약: 무슨 일이 일어났는지, 영향 범위, AI의 현재 단계를 보여준다.
   - 왼쪽: 에러 로그·Kubernetes 이벤트·상태 원문을 영어 그대로 보여주고, 각 원문 옆에 한글 해석을 붙인다. 원문과 해석은 같은 근거 ID로 연결한다.
   - 가운데: 라우터 → Agent Group → 하위 Agent의 실시간 분기 흐름도. 수준 판단 이유, 상위 모델 승격, 검증 Agent 추가, 인계 분기를 노드와 선으로 보여준다. Agent를 누르면 한글 역할 설명, 모델·추론 강도, 입력 근거, 한글 결론, 원문 출력이 펼쳐진다.
   - 오른쪽: 운영자 채팅. 분석 중에는 steering으로 실행 중인 Workflow에 반영되고, 인계·종료 후에는 운영자 지시 실행 창구가 된다.
3. 운영자 지시 실행(사람 개입): 자연어 지시를 AI가 Kubernetes 변경 계획으로 바꾼다. 기존 6개 허용 조치로 제한하지 않는다. 진행 순서는 계획 → dry-run → 확인 화면 → 실행 → 검증 → 원복 수단 기록이다. 확인 화면에는 (1) 실제 변경 내용, (2) dry-run 결과, (3) 부작용(영향 대상, 서비스 중단·재시작 여부, 원복 가능성과 방법), (4) "정말 진행하시겠습니까?"가 반드시 나온다. 운영자가 명시적으로 확인한 경우에만 실행한다.
4. Secret 변경: AI는 대상 Secret과 key만 계획한다. 값은 채팅의 마스킹된 별도 입력란으로 받고, Secret 쓰기 전용 내부 처리기가 즉시 적용한다. AI에는 key 이름, 적용 성공 여부, 해시 일치 같은 값 없는 결과만 돌려준다.
5. 서비스 메시(Kiali) 제거: 메뉴, `Mesh.tsx`, 클러스터의 `istio-system/kiali`를 백업 후 제거한다. 네트워크 흐름은 Hubble과 원천 지표를 사용한다.

### 비목표

- 평가 결과 전용 화면은 만들지 않는다(기존 지시).
- Jira는 연결하지 않는다. 작업 추적은 로컬 계획 문서로 한다.
- 새 장애 유형을 추가하지 않는다. 완료 확인 10건은 기존 3개 유형에서만 고른다.
- 무인 자동 조치 정책은 넓히지 않는다. HIGH_RISK는 계속 자동 조치 없이 인계하고, 범위 확장은 운영자가 확인한 지시 실행에만 적용한다.
- Kiali 화면 이외의 클러스터 모니터링 구성(Prometheus, kube-state-metrics, Loki, Alloy, Alertmanager, Grafana, Hubble)은 제거하지 않는다.
- 새 클러스터·CNI 교체, 기존 평가 354행·모델 가격 이력 수정은 하지 않는다.

### 제약

- 모델 호출은 구독형 Codex CLI만 사용하고 API 키는 쓰지 않는다. UI와 한글 해석은 한국어만 사용한다.
- Secret 값은 LLM 프롬프트, 대화 기록, 실행 이벤트, 감사 로그, DB 어디에도 평문으로 남기지 않는다. 운영자 지시 실행 계정에는 Secret get/list/watch 권한을 주지 않는다. 이 계정은 기존 읽기 전용 API 계정·자동 조치 계정과 분리한다.
- 대체되는 기존 문구: 과제계획서의 "LLM은 사전 허용 안전조치만 요청", "Control Plane, Node, Secret 보호 / Namespace는 관찰만" 경계와 `handed_off` 이후 메시지·제어 409 정책. 대체 범위는 운영자가 명시적으로 확인한 지시 실행에 한한다.
- 클러스터 변경 전 `.e2e-tmp/revamp-p15/`에 백업하고 필요한 객체만 바꾼다. 전체 overlay apply는 하지 않는다.
- 단일 노드(CPU 34%, 메모리 44% 사용 중)이므로 수집 범위를 넓힐 때 보존 기간과 수집 한도를 함께 정한다.
- 관제 화면은 원천 데이터(Prometheus·Loki·Kubernetes API·Hubble)를 가공 없이 최대한 그대로 쓴다. 한글 해석은 원문을 대체하지 않고 나란히 붙인다.

### 성공 기준

1. 확정한 10건을 한 번에 하나씩, 같은 Namespace에 다른 장애를 겹치지 않게 재발생시킨다. 건마다 다음을 캡처와 실행 기록으로 남긴다.
   - 전체 관제 지도에 해당 자원 장애 위치가 표시되고, 클릭하면 그 사건의 장애 관제 화면으로 이동한다.
   - 장애 관제 화면에 원문(영어)과 한글 해석이 같은 근거 ID로 나란히 보이고, 상단 한글 요약에 장애 내용·영향 범위·AI 단계가 나온다.
   - 흐름도가 실시간으로 라우터 → Group → 하위 Agent 순으로 분기한다. Agent별 역할·모델·근거·결론을 열어 볼 수 있다.
   - 사람 개입 없이 자동 복구·검증·원복 확인까지 완결된다.
2. 10건 중 인계로 끝난 건은 실패로 기록하고 원인을 조사한다. 다른 사례로 바꾸지 않는다.
3. 사람 개입 기능(steering, 인계 후 지시 실행, 부작용 확인, Secret 입력)은 자동 시험으로 검증한다. 실제 시연은 사용자가 요청할 때 함께 진행한다. Secret 경로는 표식 값(sentinel)으로 LLM 입력·기록·DB·로그에 값이 남지 않음을 자동 시험으로 확인한다.
4. 데스크톱·태블릿·모바일(1440/768/375px)에서 두 대시보드의 텍스트 잘림·겹침·가로 넘침이 없어야 한다. 기존 API·프런트·브라우저 회귀 시험이 모두 통과해야 한다.
5. Kiali 제거 후에도 유지 대상 모니터링 구성이 정상 동작하고, 관제 화면이 그 원천 데이터를 표시함을 재조회로 확인한다.

### 가정 (인터뷰에서 직접 확인하지 않음)

- steering: 운영자 메시지는 현재처럼 다음 노드 경계에서 반영한다. 반영 시점과 대상 Agent를 채팅과 흐름도에 함께 표시하고, AI는 메시지를 어떻게 해석했는지 한글로 답한다. steering으로 가능한 일은 조사 방향 변경, 특정 Agent 재실행·상위 모델 승격, 검증 Agent 추가, Group 변경, 분석 중단이다. 진행 경로를 바꾸는 steering은 흐름도에 새 분기로 남긴다. 분석 중에도 클러스터 변경을 요구하는 메시지는 확인 절차를 거친다.
- 영향이 큰 대상(kube-system, Control Plane, Node, 클러스터 범위 리소스)은 부작용 설명에 "클러스터 전체 영향" 경고를 강조한다. 확인 절차는 동일하게 한 번이다.
- Envoy sidecar 지표 수집 작업은 주 Prometheus로 옮겨 지도 연결선(요청 수·오류율·지연)에 사용한다. 중복 인스턴스인 mesh-prometheus만 제거하고, istiod와 sidecar는 유지한다.
- Pod 지표와 로그 수집 범위를 Secret을 제외한 전체 Namespace로 넓힌다.
- 한글 해석은 저비용 모델(gpt-6-luna/low)로 생성하고, 사건 비용에 포함해 표시한다. 해석은 화면 표시용이며 라우팅 판단에는 쓰지 않는다.
- 검토 기록과 설정(그룹 모델 편집) 화면은 유지한다. 기존 사건 목록은 장애 관제의 진입 목록으로 통합한다.
