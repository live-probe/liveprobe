# 에이전트 자율 조치 규칙 — 정책 C (2026-10-05, 사용자 결정)

## 원칙
1. **HIGH_RISK만 운영자 인계.** SIMPLE·NORMAL·COMPLEX는 AI가 로그와 근거를 읽고 원인을 판단해, 쿠버네티스 안에서 할 수 있는 조치를 직접 실행한다.
2. **쿠버네티스로 고칠 수 있는 것만 고친다.** Spring 코드 예외, 잘못된 쿼리, 쿠버네티스 밖 의존성 문제는 조치하지 않고 인계한다(에이전트 프롬프트에 명시).
3. **AI는 제안만 하고, 실행은 검증된 실행기가 한다.** 모델이 만든 명령을 그대로 실행하는 경로는 없다.

## AI가 제안할 수 있는 조치 (한 사건에 하나)
| 조치 | 용도 | 제한 |
|---|---|---|
| rollout_undo | 잘못된 이미지·설정 배포 | 이전 리비전이 있을 때만 |
| rollout_restart | 프로세스 상태 꼬임 | 대상 Deployment 1개 |
| pod_delete | 특정 파드만 재생성 | 컨트롤러 소유 파드, 소유 라벨 필수 |
| scale_replicas | 복제 수 조정 | 1..2 |
| set_memory_limit | OOMKilled | 256..768Mi, request 이상 |
| configmap_restore | 설정 되돌리기 | 승인된 불변 버전만(현재 승인 목록 비어 있어 항상 거부) |

## 실행 전 통과해야 하는 단계 (모두 코드로 강제)
1. 독립 검증자가 원인을 지지함(그룹: group_verifier 지지, 워크플로: 분석자와 검증자가 같은 조치에 동의, single: 신뢰도 기준).
2. 조치 종류가 허용 목록(`cfg.allowlist`)에 있고 파라미터가 형식·범위를 통과.
3. 조치 대상이 사건의 워크로드와 같음. 다른 워크로드 변경 거부.
4. 정책: 수준별 기본값 auto(HIGH_RISK는 handoff). 전역 approval·suggest_only와 사건별 모드가 여전히 더 엄격하게 덮어씀.
5. 실행기: 변경 전 스냅샷, 낙관적 동시성(resourceVersion 검사), 실행 후 롤아웃 검증, 실패 시 보상.

## 권한 분리
- API 본체의 서비스 계정은 읽기 전용이고 admission 정책이 대상 쓰기를 거부한다(실측: patch → 403).
- 쓰기는 별도 계정 `safe-action-executor`만 한다. 권한은 `inventory`·`order` 두 Deployment의 get/patch와 대상 네임스페이스의 컨트롤러 소유 파드 삭제뿐이다(실측: loadgen·Service·Secret·생성은 모두 no).
- 추가 admission 정책 `safe-action-executor-bounds`: 복제 1..2, 메모리 256..768Mi, 이미지·환경변수·볼륨·셀렉터 불변.
- 토큰은 이 파드에만 읽기 전용으로 마운트되고 없으면 조치가 닫힌 채로(실패) 인계된다.

## 이번 정책으로 바뀐 것 (사실)
- 이전(정책 A/B)에서는 롤백 하나뿐이라 OOM·지연·풀 점유·크래시 22개 사례가 구조적으로 0%였다.
- 이제 `rollout_restart`, `pod_delete`, `set_memory_limit`, `scale_replicas`가 AI 경로에 연결됐다.
- 한계: 앱 내부 장애(chaos 풀 점유, 지연)는 재시작으로 해소되는 것처럼 보여도 원인은 앱 쪽일 수 있다. 이 구분은 평가에서 "해결 여부"와 "올바른 판단"을 따로 본다.

## 앱 원인이지만 쿠버네티스로 완화할 수 있는 경우
- 시작할 때마다 죽는 앱(예: exit 70 크래시)은 재시작해도 소용없으므로 인계한다.
- 원인은 앱에 있어도 피해가 실행 중인 프로세스 안에 있으면(연결 풀 고갈·누수, 스레드 멈춤), 재시작이나 파드 삭제로 서비스를 먼저 살린다. 이때 `why`에 "임시 조치이며 근본 원인은 개발자 확인 필요"를 남긴다.

## 시험 중 발견한 수정 (2026-10-11)
1. **앱 지표 미수집**: Istio의 메트릭 병합이 수집 주소를 :15020으로 바꿨지만 NetworkPolicy가 8080만 허용해서, AI에게 요청률과 5xx가 항상 0으로 보였다. inventory·order에 `prometheus.istio.io/merge-metrics: "false"`를 설정해 해결했다(Kiali 메시 지표는 :15090을 쓰므로 영향 없음). Istio 도입 이후의 정책 A·B 평가도 같은 상태였을 수 있다.
2. **근거 보강**: 평균 지연, DB 연결 풀(사용 중·최대·대기·획득 실패)을 AI 근거에 추가했다. 추가 지표 조회가 실패해도 기존 지표는 유지한다.
3. **평가 장치**: 이전에는 장애가 풀려도 150초 동안 다시 주입해서, AI가 고쳐도 다시 깨지는 구조였다. 이제 파드나 Deployment가 바뀌면 재주입을 멈춘다.
4. **승인 하한**: 조치별 승인 하한을 approval에서 auto로 바꿨다. 실행 시점에 사건 수준과 전역 모드로 정책을 다시 계산하므로, 위조된 auto 행도 HIGH_RISK나 전역 approval 상태에서는 거부된다(테스트로 확인).
5. **라우터**: LLM 혼자 HIGH_RISK로 올리지 못한다(규칙만 가능). 워크로드 자체가 죽어 엔드포인트가 0인 경우는 라우팅 장애로 보지 않는다.
