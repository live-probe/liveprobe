# P18 확장 방향 인터뷰 — 쿠버네티스 애플리케이션 장애 대응과 통합 관제실

상태: 기본 범위 합의 및 사용자 추가 요구 반영. 구현·배포 완료를 뜻하지 않는다. 통합 관제실 추가 요구는 `P18-incident-conversation-brief.md`에 정리했다.

## 출발점 (사용자 원문 요지, 2026-10-24)
- LiveProbe는 크게 네 부분으로 나뉜다: 1) 장애 감지·판단 2) Group 선택 3) 장애 분석 4) 장애 조치.
- 단계마다 따로 쓸 수 있게 이미지 4개로 분리하는 모듈화를 생각했다. 다만 지금은 한 덩어리로 가는 게 맞아 보인다고 직접 판단했다.
- 핵심 바람: 지금은 쿠버네티스 장애만 다루지만, 나중에는 스프링부트·파이썬 서버 같은 다른 서버 자원의 에러에도 대응할 수 있었으면 한다.
- 어려운 점:
  - 쿠버네티스는 같은 네트워크 안에서 바로 조치할 수 있다.
  - 애플리케이션은 대개 개발 환경이 따로 있고, dev → stg → prd 배포 정책을 따른다.

## 저장소에서 확인한 현재 경계 (코드 기준)
| 단계 | 현재 위치 | 쿠버네티스 의존 |
|---|---|---|
| 감지·판단 | `watcher.py`(Pod·Event·Endpoint 감시), `/api/alerts`(Alertmanager), `incidents.py` `Signal{namespace, kind, name, reason, source}` → 지문·병합 | 신호 형태가 namespace/Deployment 중심 |
| 근거 수집 | `evidence.py` `Bundle`(Kubernetes·Prometheus·Loki) | 수집기 3종이 쿠버네티스 객체 기준 |
| Group 선택 | `router.py` `extract_features(Bundle)` → `rules_decide` / LLM 분류 → `Decision(level, workflow)` | 특징값이 Pod 재시작·엔드포인트 등 쿠버네티스 지표 |
| 분석 | `workflows.py` 수준별 그래프, `agent_groups.py`, RAG | 프롬프트·근거 ID가 쿠버네티스 근거 기준. 구조 자체는 범용 |
| 조치 | `proposals.py` 조치 목록(rollout_undo 등 6종), `actions.py`·`safety.py` 검증·실행, `commands.py` 운영자 지시 | 전부 Kubernetes API 쓰기 |
- 과제계획서 적용 대상: 쿠버네티스 클러스터와 그 안의 워크로드. 1차 MVP는 클러스터 1개, 네임스페이스 1개, 장애 Family 4종이다. 애플리케이션 종류와는 무관하게 연결할 수 있지만, 그 연결은 표준 쿠버네티스 상태·로그로 한정한다.

## 확인 내용 (질문과 답, 한 줄씩)
- Q1 운영(prd) 애플리케이션 에러에서 AI가 어디까지 직접 하나? → 소스 수정이 필요한 에러는 수정 PR을 만들어 기존 dev → stg → prd 파이프라인에 태우고, 단계마다 사람이 승인한다. 트래픽 조정·버전 롤백 같은 운영 조치는 지금 쿠버네티스에서 하던 방식(허용 목록, 승인·원복 안전장치) 그대로 한다.
- Q2 대상 애플리케이션은 어디서 실행되나? → 모두 쿠버네티스 안에서 실행된다. dev·stg·prd는 클러스터 또는 네임스페이스로 구분된다.
- Q3 무엇을 보면 확장이 됐다고 판단하나? → 로컬 끝단 실연까지 한다. 운영 관제의 네임스페이스는 dev·stg·prd 3개로 둔다. 각 환경에는 시스템 단위로 띄운다. 기존 order·inventory는 시스템 `order`로 태그한다(`liveprobe-target` 묶음의 이름을 order로 바꿈). loadgen 등 나머지는 띄우지 않는다. 시스템 5개를 추가하며, 각 시스템은 실제 접속 가능한 화면이 있고 사용자가 직접 장애를 낼 수 있어야 한다.

## 추가 요구 (사용자가 직접 제시)
- 기존 02 근거·단계 상세와 03 운영자 대화를 하나의 02 채팅으로 합친다. 기본 화면은 01 AI 분석 흐름 + 02 분석·운영자 대화다.
- 01 실행 블록을 누르면 정확한 실행의 채팅 카드로 부드럽게 스크롤·강조한다. 카드에는 개요·한글 결론과 단계 고유 내용을 기본 표시한다.
- 근거 수집이 9건이면 실제 9개 항목 각각의 이름·짧은 내용·상태를 보여 준다. 신호 분석과 결과 확인은 같은 근거 목록 반복이 아니라 각각 분석 결과와 검증 결과를 보여 준다.
- 카드의 상세보기를 누를 때만 기존 03 폭의 오른쪽 패널을 열고 닫으면 없앤다. 운영자 입력은 02에 둔다. 기존 승인·Secret·PR 승격 안전 경계는 유지한다.
- 실제 `/incidents/1019`에서 감지 신호·사건 수준 판단 선택 시 결론·연결 근거 없음 표시를 재현했다. 상세 요구·데이터 대응·검증 기준: `docs/plans/revamp/P18-incident-conversation-brief.md`.

## 정리된 요구 (기본 범위 합의와 화면 추가 요구 반영)
### 목표
- 환경 축(dev → stg → prd)과 시스템 축(order + 신규 5개)으로 운영 관제를 재구성한다. 한 장애는 "어느 환경의 어느 시스템의 어느 서버"로 표시된다.
- 조치는 두 갈래로 나눈다.
  - 운영 완화(롤백·재시작·스케일·트래픽): 기존 쿠버네티스 방식 그대로 한다.
  - 근본 수정(소스 변경): 수정 요청(PR에 해당)을 만들고 dev → stg → prd 순서로 승격한다. 각 단계마다 운영자가 부작용 설명을 보고 "정말 진행하시겠습니까?"를 확인한다.
- 분석은 "운영 완화로 막을 수 있는가 / 코드 수정이 필요한가"를 근거와 함께 판정한다. 근거에는 애플리케이션 예외와 스택트레이스가 포함된다.
- 장애 관제실은 01 흐름과 02 통합 채팅을 기본으로 하며, 흐름 선택 → 같은 실행의 요약 카드 이동 → 필요한 경우 상세 패널 열람으로 읽는다. 빈 공통 상세·동일 근거 반복을 단계별 내용으로 대체한다.

### 제약과 비목표
- 쿠버네티스 밖(VM·물리 서버)은 대상이 아니다. 네 단계를 이미지 4개로 분리하는 일은 지금 하지 않는다(한 덩어리 유지). 대신 단계 간 입출력 형식을 시스템·환경 중립으로 정한다.
- 기존 클러스터(`rancher-desktop` 단일 노드·flannel)를 유지한다. 새 클러스터·CNI 변경은 하지 않는다. 사용자 추가 지시로 `live-probe` organization에 시스템별 비공개 저장소와 공개 LiveProbe 저장소를 만들고, 소스 수정은 실제 GitHub PR로 검토한다. 공개 전 비밀정보·로컬 운영 자료를 제외하고 기존 로컬 이력은 업로드하지 않는다.
- 기존 안전 원칙을 유지한다.
  - 고위험은 인계하고, Secret 값은 AI가 보지 않는다.
  - 운영자 명령은 부작용을 설명하고 확인받는다.
  - 미관측 값은 0이나 정상으로 꾸미지 않는다.
- 기존 inventory DB(354행)를 덮어쓰지 않는다. 환경별 DB는 새로 만든다.
- `liveprobe-target`은 삭제하지 않는다. prd 검증 후 축소해 기록용으로 보존한다.
- 노드 자원은 할당 가능 메모리 약 11.7GiB, 현재 요청 3.8GiB다. 신규 시스템은 경량 이미지로 만들고, 사이드카는 prd에만 둔다(dev·stg는 메시 없이 운영).

### 성공 기준
1. 운영 관제에서 네임스페이스 선택지가 dev·stg·prd 3개다. 각 환경 안에 시스템 6개(order + 5)가 시스템 이름으로 묶여 보이고, 다른 대상 워크로드(loadgen 등)는 보이지 않는다.
2. 신규 시스템 5개는 각각 브라우저로 접속할 수 있는 화면이 있다. 화면에서 장애를 직접 낼 수 있고(유형별 버튼), 낸 장애는 LiveProbe 장애로 해당 환경·시스템 위치에 표시된다.
3. 실연에서 다음이 끊김 없이 관측된다.
   - prd order 서비스에 코드 버그를 주입한다.
   - 감지한다.
   - 분석이 "코드 수정 필요" 판정과 근거(스택트레이스·소스 위치)를 낸다.
   - prd에서 운영 완화(롤백)를 한다.
   - 수정 요청을 생성한다(diff·단위 시험 결과).
   - dev 배포·검증 → 승인 → stg 배포·검증 → 승인 → prd 배포·검증을 진행한다.
   - 각 승인 전에 부작용 설명과 확인 질문이 나온다.
   - 실패 시 해당 단계를 원복한다.
4. 기존 회귀(백엔드·화면 단위·모의/실배포 브라우저)가 통과한다.
5. 통합 관제실 추가 요구의 U1~U8을 검증한다. 특히 9건 수집의 9개 요약, 단계별 서로 다른 내용, 정확한 실행 카드 이동, 상세 열기/닫기, 02 메시지 입력이 실제 화면에서 동작해야 한다.

## 결정 사항
- 조치를 두 갈래로 나눈다.
  - 운영 완화: 코드를 바꾸지 않는 즉시 조치. 기존 쿠버네티스 조치 경로와 안전장치를 그대로 쓴다.
  - 근본 수정: 소스 변경 PR → dev → stg → prd 단계 승격. 각 단계마다 사람이 승인하며, AI가 운영에 직접 배포하지 않는다.
- 분석 단계는 "운영 조치로 완화 가능한가"와 "소스 수정이 필요한가"를 구분해 판단해야 한다(근거 포함).
- 감지·근거 수집·운영 완화는 기존 쿠버네티스 경로를 재사용한다. 새로 필요한 것은 애플리케이션 에러 신호(예외·스택트레이스), 소스 저장소 연결, 배포 파이프라인 연결이다. 쿠버네티스 밖(VM·물리 서버) 지원은 비목표다.
- 저장소 사실: 참조 서비스 `services/order`·`services/inventory`는 이미 스프링부트(Maven, Java 21)이고 이 저장소 안에 소스가 있다. 현재 환경은 단일 클러스터 1개(`liveprobe-target` 하나)이며, dev·stg·prd 구분은 없다.

## 미결·가정
- 추가 화면 요구는 명시적이므로 새 질문으로 기존 인터뷰를 반복하지 않는다. 반응형은 흐름/대화 두 전환과 전체 폭 상세 서랍, 이동은 네이티브 스크롤·움직임 감소 분기를 권장 기본값으로 기록했다.
- 채팅과 흐름을 실행 ID로 연결하고, 과거 기록이 부족하면 미기록 사유를 표시한다. 존재하지 않는 결론·근거를 만들어 내지 않는다.
- 새 요구는 계획 편입 상태이며 구현·통합·배포·시각 검증은 별도 완료 증거가 필요하다.
