# 60개 사고 상황 × 4가지 방식 평가 계획

## 1. 목적

"사건 수준에 맞춰 AI 구성을 바꾸는 방식(Adaptive)"이 다른 방식보다 원인 분석 품질을 유지하면서 더 효율적인지 같은 조건에서 비교한다.
지금 진행하는 것은 학습·테스트 단계이고, 이후 시연에서 사건을 하나씩 터트리며 가장 좋은 구성을 찾아가는 과정을 거친다.

## 2. 현재 상태 (사실만)

- 60개 사고 상황 목록과 정답표는 있다: `chaos/cases/F*.yaml`. **정답표 사람 검토는 미확인.**
- 평가 실행 뼈대는 있다: `evaluation/harness/` (순차 실행, 재개, 정답 유출 차단). 가짜 실행기로 테스트만 통과했다 (evaluation 61개, chaos 15개).
- 진짜 AI로 돌린 실험 결과는 **0건**이다. 240건은 아직 하나도 실행하지 않았다.
- 4가지 방식의 모델 값은 `approval="draft_pending_KAN-58"` 초안이며 사람 승인이 없다.
- 현재 지시: AI 호출은 모두 제외하고 테스트 케이스 작성에 집중.

## 3. 60개 사고 상황

유형(Family)별 15개씩, 합계 60개. ID 규칙 `F<유형>-<번호>`.

| 유형 | 내용                                    | 개수 | ID            |
| ---- | --------------------------------------- | ---- | ------------- |
| F1   | 이미지 문제 / 반복 재시작 (image_crash) | 15   | F1-01 ~ F1-15 |
| F2   | 메모리 부족으로 종료 (oom)              | 15   | F2-01 ~ F2-15 |
| F3   | 응답 지연 / DB 연결 고갈 (latency_pool) | 15   | F3-01 ~ F3-15 |
| F4   | 서비스 연결 끊김 (endpoint_loss)        | 15   | F4-01 ~ F4-15 |

- 같은 유형 안에서 원인, 대상 서비스(A/B), 가짜 단서(decoy), 근거 충분 여부를 다르게 섞는다.
- AI에게는 **공개 항목만** 준다: id, family, target, expected_signal, baseline_checks. 정답 원인·기준 Workflow·기대 대응은 절대 주지 않는다.

## 4. 4가지 방식 (arm)

실험 시작 전에 고정하고, 결과를 본 뒤에는 바꾸지 않는다. 아래 값은 현재 초안이다.

| 방식              | 구성                                                                     |
| ----------------- | ------------------------------------------------------------------------ |
| Single-small      | 가장 작은 모델 하나(Luna/low)가 전부 수행                                |
| Single-High       | 가장 큰 모델 하나(Sol/xhigh)가 전부 수행                                 |
| Fixed Multi-Agent | 모든 사건에 같은 "복잡 Group"을 고정 사용, 역할별 모델 혼합              |
| Adaptive          | 라우터가 사건 수준을 판단해 Group을 고르고, 역할별로 Luna/Terra/Sol 혼합 |

- 역할 5개: 라우터, 신호 분석, 결과 확인, 근거 정리, 안전 검증.
- 비교 공정성 조건: 같은 시작 상태, 같은 근거 시간대, 같은 공개 입력, 방식별 프롬프트 버전 고정.

## 5. 실행 순서 (모든 실행은 직렬, 한 번에 하나)

사건-방식 쌍 240개(60×4)를 사건 순서대로 하나씩:

1. 현재 상태가 정상 기준선인지 확인
2. 장애 주입
3. 공개 입력만으로 해당 방식 실행
4. **성공/실패와 무관하게 항상 원복**, 기준선 회복 확인
5. 기록 저장 (모델, 버전, 입력, 출력, 시간, 결과)

중단 조건: 원복 실패(해당 네임스페이스 격리, 다음 사건 금지) / 정답 유출 감지 / 구독 사용 한도 도달(멈췄다가 재개, API로 전환하지 않음).
재개: 이미 검증 완료된 쌍만 건너뛰고, 중단된 실행은 "실패"로 남겨 명시적으로 재실행한다. 재시도해도 정식 완료 기록은 쌍당 1건.

## 6. 측정 지표 (KAN-59)

정의는 `evaluation/metrics/definitions.py`(`kan59-metrics/v1`)에 고정. 정답표는 채점 단계에서만 오프라인으로 사용.
주요 지표: Workflow 선택 정확도, 과소/과잉 구성률, 고성능(Sol급) 모델 호출 감소율, 원인 후보 top-3 적중률 등. 결측·실패 실행은 0으로 세지 않고 분모에서 별도 표기한다.
비용 관련 지표가 있다면 실측 기록용이며 실행을 막는 상한으로 쓰지 않는다.

## 7. LLM 사용 방식

- 구독형 CLI(codex_cli/claude_cli)만 사용한다. API 키는 쓰지 않는다.
- 비용 예상치와 금액 상한은 두지 않는다.
- 시연 단계에서는 사건을 하나씩 실행하며 결과를 보고 구성을 조정해 최적 조합을 찾는다. 단, 조정 이력은 기록하고, 정식 비교 실험(240쌍)은 방식 고정 후에 실행한다.

## 8. 실행 전 필요한 결정 (미결)

1. 4가지 방식의 정확한 모델·추론 강도·프롬프트 확정 (사람 승인)
2. 60개 정답표 검토(KAN-90) 완료
3. 240회 실제 장애 주입을 돌릴 격리 환경과 독점 시간대 (다른 장애 시험과 동시 금지)
4. 현재 "AI 호출 제외" 지시 해제 시점

## 9. 완료 기준 (정직한 정의)

가짜 실행기 결과나 합성 fixture는 **완료로 세지 않는다.** 저장된 실제 실행 기록으로 60개 사건 × 4방식 = 240쌍이 각각 검증되고, 매 실행 후 기준선 회복이 확인되어야 완료다.
